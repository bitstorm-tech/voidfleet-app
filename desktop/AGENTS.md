# Desktop (Electron)

Voidfleet als ausführbare Datei. Electron statt Electrobun, weil es auf allen Systemen dasselbe Chromium mitbringt: WebGL/WebGPU für Babylon.js verhält sich überall gleich (Electrobun nutzt sonst die System-Webview, unter Linux WebKitGTK mit schwachem WebGL).

- `bun install` (lädt per `postinstall` das Electron-Binary), dann `bun run start` (baut und startet die App), `bun run dist` (Paket für das aktuelle System nach `release/`: Linux AppImage + entpackt, Windows NSIS-Installer + portable EXE, macOS DMG), `bun run typecheck`.
- `src/main.ts` — Hauptprozess: setzt das Icon (`dist/icon.png`, beim Bauen aus `client/assets/app/icon-512.png` kopiert) am Fenster für Linux und im Dock von macOS, das beim Entwickeln sonst das Electron-Icon zeigt; gepackt tragen Windows- und macOS-App es ohnehin, sucht einen freien Port, startet den Spielserver mit `PORT` und `HOST=127.0.0.1`, wartet auf seine Startzeile und zeigt ihn im Fenster (F11 Vollbild, F12 DevTools, kein Menü, eine Instanz). Der Server endet mit der App. Die Einstellungen des Clients speichert er als `settings.json` im Datenordner der App (`app.getPath("userData")`, unter Linux `~/.config/Voidfleet`), weil der `localStorage` am Origin samt wechselndem Port hängt.
- `src/preload.ts` — reicht die Einstellungsdatei per IPC als `window.voidfleetDesktop` an `client/src/settings.ts` durch.
- Der Spielserver läuft als eigene Binary: `bun build --compile` macht aus `../server/src/main.ts` die Datei `dist/voidfleet-server`, in die Bun den gebündelten Client samt Assets einbettet. Electron-Builder legt sie in die Ressourcen der App (`extraResources`). Gebaut wird immer für das System, auf dem `bun run build` läuft.
- Matches leben im Server der App; der Match-Link zeigt auf `127.0.0.1` und taugt nicht zum Teilen. Gespielt wird darin gegen den Computergegner.
